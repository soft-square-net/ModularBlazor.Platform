> **Status: phases 1–4 of 7 are done** on branch `feat/rebuild` of the repository `ModularBlazor.Module.Storage`
> (module `storage` 0.1.0). **Phase 5** (recycle bin, versions, purge and garbage collection) **is in progress**, and
> phases 6–7 are planned. This page describes the committed code up to phase 4. The Files page needs MudTail's explorer
> component, which is on the Platform branch `feat/mudtail-explorer` and not merged yet.

**Storage** keeps a tenant's folders and files. The tenant database is the source of truth: the tree, the versions and
the access lists are rows. The blob store holds only the bytes. What a user may do with an item is decided by the
module's own **NTFS-style access lists**. The platform permissions only open the door to Storage.

## Architecture

The server part follows Ardalis Clean Architecture, adapted to a runtime module, like Contents.

| Part | Project | What it is |
| --- | --- | --- |
| Core | `src/WebApi.Modules.Storage.Core` | Aggregates: `Item` (files and folders, `FileVersion`), `AccessEntry` and `AccessEvaluator`, `StorageGroup`, `Blob`, `UploadSession`. Also the Windows name rules (`ItemNames`) |
| Use cases | `src/WebApi.Modules.Storage.UseCases` | Mediator commands and queries that return an Ardalis `Result`. The blob store ports (`IBlobStore`, `IBlobStores`), placements, quotas and `StorageOptions` |
| Infrastructure | `src/WebApi.Modules.Storage.Infrastructure` | `StorageDbContext` (schema `storage` in each tenant database), with tenant migrations for PostgreSQL, SQL Server, MySQL and Oracle. Blob stores: `FileSystemBlobStore` and `S3BlobStore` (AWS SDK; MinIO with path-style addressing) |
| Web (entry) | `src/WebApi.Modules.Storage.Web` | `StorageModule : IRuntimeModule`, the Carter route table `StorageRoutes` under `/api/storage`, the endpoints, and the signed download tickets |

## The model

- **Items.** Every file and folder is a row (`storage.items`) with a materialized path (`/{id}/{id}/…/`). The other
  tables are `file_versions`, `blobs`, `uploads`, `access_entries`, `groups` and `group_members`.
- **Blobs** are stored under keys the module makes (`t/{tenant}/{yyyy}/{MM}/{id}`). Copies share a blob, which is
  reference counted. Every upload of an existing file makes a new version.
- **Top folders** are created per tenant on first use (`GET /roots`):
  - `Files` is shared. Everyone gets *Read & execute* on this folder only; admins grant the rest.
  - `Users` holds the homes. Everyone may pass through it, but nobody may list it.
  - One **home** per user, named by the user id. Only that user has full control.
- **Names** follow the Windows rules. These characters are not allowed: `\ / : * ? " < > |`. Reserved names are not
  allowed, and names must be unique per folder, ignoring case.
- **Delete** is a soft delete into the recycle bin. The recycle bin itself is phase 5.
- **Placement and quota.** Each tenant has a placement (a named connection, a bucket and a key prefix) and an optional
  quota. A blob remembers where it was written, so a new placement applies only to new files. The quota counts what the
  tenant keeps (every version, and a blob shared by copies only once) plus uploads in progress.

## Permissions and access model

### Platform permissions (the gate)

| Permission | Lets the caller |
| --- | --- |
| `storage.access` | Use Storage at all: their home folder, and whatever the access lists open to them |
| `storage.admin` | Bypass the access lists (full control of every item in the tenant), set any owner, and manage Storage groups. Later also connections, quotas and the recycle bin |

Every route needs `storage.access` or `storage.admin`. There are two exceptions. Group administration (`POST`, `PUT`
and `DELETE /groups`) needs `storage.admin`. The signed download link `GET /links/{token}` is anonymous, because the
signature is the authorization.

### The module's own ACL

Every item has an owner and an access list of **allow** and **deny** entries (`AccessEntry`).

**Principals**

| Kind | Who it matches |
| --- | --- |
| `User` | One member, by the token's `sub` |
| `Everyone` | Every member of the tenant who may use Storage |
| `Permission` | Whoever holds a platform permission in a scope right now, for example `content.editor` in `press:daily`. Shift grants therefore give access only while the shift runs |
| `Group` | A Storage group |
| `CreatorOwner` | NTFS CREATOR OWNER: on a folder, each new item inherits it as an entry for that item's owner |

**Rights** (`StorageRights`) use the NTFS values: `ListFolder`/read data, `CreateFiles`/write data,
`CreateFolders`/append data, `ReadExtendedAttributes`, `WriteExtendedAttributes`, `Traverse`/execute, `DeleteChildren`,
`ReadAttributes`, `WriteAttributes`, `Delete`, `ReadPermissions`, `ChangePermissions` and `TakeOwnership`. Storage adds
its own `Share` right (`0x1000000`). The presets of the Windows Security dialog are combinations of these: `Read`,
`Write`, `ReadAndExecute`, `Modify` and `FullControl`. The API sends rights as the integer flag value.

**Inheritance flags** (`AceInheritance`): `Subfolders` (container inherit), `Files` (object inherit), `NoPropagate`
(direct children only) and `InheritOnly` (not on the folder itself). "This folder, subfolders and files" is
`Subfolders | Files`. Entries on files use `None`.

**Evaluation.** The evaluator runs on read, along the item's chain of folders. Inherited entries are never copied down,
so moving a folder takes effect at once.

1. The entries are put in canonical order: the item's own denies, then its own allows, then each ancestor's inheritable
   entries (denies before allows), nearest folder first. The chain stops at the first item that does not inherit.
2. For each right, the first entry that names it decides. An explicit allow therefore beats an inherited deny, as in
   Windows.
3. The owner may always read and change the permissions.

**More rules**

- Inheritance can be broken on an item. The inherited entries are then either converted to explicit ones or dropped.
- Listings show only the items the caller has some right on (access-based enumeration).
- The client gets the caller's effective rights on every item and disables refused commands. The server checks again on
  every call.
- Rename, move and delete need `Delete` on the item, or `DeleteChildren` on its folder. New folder needs
  `CreateFolders`, and upload needs `CreateFiles`.

## API reference

The routes are under `/api/storage`. They are tenant-bound: the tenant comes from `X-Tenant`, the host name or the
token. Responses use the records in `UseCases` (`ItemDtos.cs`, `Uploads.cs`, `AccessUseCases.cs`, `Groups.cs`). The
OpenAPI document is `src/openapi/storage.json`.

`ItemDto` is the shape used everywhere: `id, kind, role, parentId, name, extension, size, contentType, currentVersion,
ownerId, inheritsAccess, createdAt, createdBy, modifiedAt, modifiedBy, version, rights, hasSubfolders`. `version` is the
concurrency token. `rights` holds the caller's effective `StorageRights`.

### Items

| Method and route | Request → response |
| --- | --- |
| `GET /roots` | → `Roots {files, home}`. Creates `Files`, `Users` and the caller's home on first use |
| `GET /usage` | → `StorageUsage {used, pending, quota}`. `quota` is null when there is none |
| `GET /folders/{id}/items` | → `FolderView {folder, path: Crumb[], items}`. Folders come first. Needs List folder |
| `GET /items/{id}` | → `ItemDetail {item, path, versions: VersionDto[]}` |
| `POST /folders` | `{parentId, name, numberIfTaken}` → 201 `ItemDto`. With `numberIfTaken`, a taken name gives "New folder (2)" |
| `PATCH /items/{id}` | `{name, version?}` → `ItemDto` (rename) |
| `POST /items/move`, `POST /items/copy` | `{ids[], targetFolderId}` → `BatchResult {done: ItemDto[], failed: [{id, reason}]}`. Copies inherit from the destination. `Storage:MaxCopyItems` limits a copy |
| `POST /items/delete` | `{ids[]}` → `BatchResult`. Items go to the recycle bin |
| `GET /items/{id}/content?version=&inline=` | The file's bytes, from the current version or another one. Range requests are supported |
| `GET /items/{id}/link?version=&inline=` | → `DownloadLink {url, expiresAt}`, valid for `Storage:DownloadLinkLifetime`. On S3 it is presigned (the bytes go straight from the bucket); on the disk it is the module's signed `GET /links/{token}` |
| `GET /links/{token}` | Anonymous: streams the file of a valid signed link |

### Uploads (resumable, in chunks)

| Method and route | Request → response |
| --- | --- |
| `POST /uploads` | `{folderId, name, size, contentType?, conflict}` → `UploadDto {id, folderId, name, size, chunkSize, received, conflict, expiresAt}`. `conflict` is `Fail`, `Replace` (a new version) or `KeepBoth` |
| `PUT /uploads/{id}/chunks?offset=` | Multipart form file `chunk`, at the offset the upload expects → `UploadDto` |
| `GET /uploads/{id}` | → `UploadDto`. Send the next chunk at `received` |
| `POST /uploads/{id}/complete` | → `ItemDto`. The file appears in the folder, or becomes a new version |
| `DELETE /uploads/{id}` | Cancels the upload and drops its bytes |

Chunks are 8 MiB by default (`Storage:ChunkSize`). On S3, each chunk is one part of a multipart upload, and parts must
be at least 5 MiB. A file has at most 500 chunks, so big files use bigger chunks. Unfinished uploads expire after
`Storage:UploadLifetime`.

### Access and groups

| Method and route | Request → response |
| --- | --- |
| `GET /items/{id}/acl` | → `AclDto {itemId, kind, ownerId, inheritsAccess, version, entries: AceDto[]}`. The item's own entries come first, then the inherited ones with `inheritedFromId` and `inheritedFromName`. Needs Read permissions |
| `PUT /items/{id}/acl` | `{inheritsAccess, entries, convertInherited, version}` → `AclDto`. Needs Change permissions |
| `PUT /items/{id}/owner` | `{ownerId?}` → `AclDto`. Without an id, the caller takes ownership (Take ownership). Giving ownership to someone else needs `storage.admin` |
| `GET /items/{id}/effective-access?userId=` | → `EffectiveAccessDto {userId, rights, isAdmin, canUseStorage}` |
| `GET /groups` | → `GroupDto[] {id, name, description, members[], version}`, for the principal picker |
| `POST /groups`, `PUT /groups/{id}?version=`, `DELETE /groups/{id}` | `storage.admin`. The body is `{name, description?, members?}`. Entries that name a deleted group match nobody |

An `AceDto` has these fields: `principalKind`, `principalId`, `principalScope`, `type` (`Allow`/`Deny`), `rights`,
`inheritance`, `inherited`, `inheritedFromId` and `inheritedFromName`.

### Errors

Errors are problem-details responses. Use-case results are mapped as follows (`ResultExtensions`,
`StorageProblemsFilter`):

| Status | When |
| --- | --- |
| 400 | Invalid input, for example uploading into a file |
| 401 | Not signed in |
| 403 | No `storage.access` or `storage.admin`, or the ACL refuses the action |
| 404 | No such item, upload or version; content missing from the blob store; an invalid or expired link |
| 409 | A name is taken (with `Fail`); the quota would be exceeded; an incomplete upload is completed; a file would replace a folder; a domain rule (an invalid name, a system folder); a concurrency conflict (`version` is stale, or a name was taken at the same moment) |
| 503 | A dependency is unavailable |

Batch endpoints (`move`, `copy`, `delete`) do not fail as a whole. Each item that fails is listed in `failed` with its
reason.

## Settings and secrets

There are two kinds of settings:

- **Module settings** have their defaults in the manifest and are changed in the admin area.
- **Host overrides** (`Modules:Settings:storage:{key}`) come from environment variables, user secrets or a vault. They
  reach the module but are never written to the module catalog. **Keys and secrets belong here.**

| Key | Default | Notes |
| --- | --- | --- |
| `Storage:MaxFileSize` | 2 GiB | |
| `Storage:ChunkSize` | 8 MiB | |
| `Storage:UploadLifetime` | `1.00:00:00` | |
| `Storage:DownloadLinkLifetime` | `00:10:00` | |
| `Storage:MaxCopyItems` | `10000` | |
| `Storage:Local:Root` | empty, which means `%LocalAppData%/ModularBlazor/storage` | Every replica must see the same folder |
| `Storage:Connections:{name}:Kind` | `S3` | `S3` or `Local` |
| `…:ServiceUrl`, `…:Region` | empty, `us-east-1` | S3 endpoint (empty for Amazon S3) and region |
| `…:AccessKey`, `…:SecretKey` | empty | **Secret, host overrides only.** When empty, the default AWS credentials are used (for example an instance role) |
| `…:ForcePathStyle` | `false` | `true` for MinIO |
| `…:PublicUrl` | empty | The endpoint browsers reach, when the API reaches S3 at another address. Links are presigned for it |
| `…:CreateBucket` | `false` | Create a missing bucket on first use (development) |
| `…:Root` | | Local connections: blobs go under `Root/bucket/prefix` |
| `Storage:Default:Connection`, `:Bucket`, `:Prefix`, `:Quota` | | Every tenant's placement. An empty connection, or `local`, means the local disk. The quota is in bytes; 0 or empty means no quota |
| `Storage:Tenants:{tenant}:…` | | The same keys for one tenant. They override the default key by key |

If you remove a connection that blobs were written to, those files become unreadable, and the error names the
connection. The repository README has a full example with environment variables. Never commit real keys.

## UI pages

| Route | Page | What it does |
| --- | --- | --- |
| `/files` (`?folder={id}` opens that folder) | Files | MudTail's Windows 11 style explorer. The navigation pane has places (My files, Files), a folder tree and Quick access (pinned folders, kept in the browser). The page also has the address bar, the command bar and the context menu |

Commands that work today:

- Browse folders, and search within the open folder.
- New folder, inline rename, cut/copy/paste and drag to move, delete.
- Upload files and whole folders. The folder structure is kept, and a taken name gets a number (`KeepBoth`).
- Download, and image previews through short-lived inline links.

The rights the API returns become the explorer's deny lists, so refused commands are greyed out. **Share**,
**Security** and **Edit** are disabled until their phases.

## Install and activation

No `.modpkg` bundle is packed yet. Until then:

1. **Platform.** For the Files page, the platform's UI.MudTail must include the MudTail explorer.
2. **Server part.** Zip the build output of `WebApi.Modules.Storage.Web`. Upload it on **Host Modules**
   (`/host-modules`) and activate it; this runs the tenant migrations. Set the connection keys as host overrides.
3. **Client parts.** Upload them on **Client Modules** (`/client-modules`), the API client first:
   `WebApi.Modules.Storage.Client`, then `Module.Storage`.
4. **Grant access.** Grant `storage.access` to users and `storage.admin` to the tenant's storage admins. After that, use
   the access lists.

The planned release is one bundle, `storage-<version>.modpkg`, with `module.json`, `server/`, `client/` and
`contracts/`. It installs the server part first, then the client parts.

To build and test: `dotnet build` and `dotnet test`. Restoring needs `GITHUB_PACKAGES_TOKEN` (`read:packages`). The S3
store tests run only when `STORAGE_TEST_S3_URL`, `STORAGE_TEST_S3_ACCESS_KEY` and `STORAGE_TEST_S3_SECRET_KEY` are
set. After an endpoint change, export the OpenAPI document again with
`Export-ModuleOpenApi.ps1 -Project …/WebApi.Modules.Storage.Web -ModuleId storage`, then regenerate the client. After a
model change, add a migration for every provider with `Add-Migration.ps1`; the README has the exact arguments.

## Developing with the playground

```bash
dotnet run --project playground --launch-profile dev -p:PlatformRoot=<a Platform checkout on feat/mudtail-explorer>/
```

The playground runs PostgreSQL, MinIO, the identity service on port 5090, one WebApi on 5080 and the client on 5070.
These are the platform lab's ports, so stop the lab first.

| Profile | What it does |
| --- | --- |
| `dev` | The module and its client parts load from their build output. Rebuild, then restart the `webapi` resource |
| `install` | Starts without the module. Each build writes `playground/out/storage.zip`, to upload on `/host-modules` |

- In Development the platform seeds the tenants `acme` and `globex`.
- `acme-admin@modular.local` gets `storage.*` in `acme`, and `editor@modular.local` gets `storage.access`, both through
  `Access:DevGrants`. The passwords are in the identity service's `appsettings.Development.json`.
- Blobs go to the MinIO bucket `storage`. The MinIO console is at http://localhost:9001; its password is the Aspire
  parameter `minio-password`, shown in the dashboard. With `Playground:Blobs=local`, blobs stay on the disk in
  `playground/.data/blobs`.
- Data stays in the Docker volumes `storage-playground-data` and `storage-playground-minio`, and in `playground/.data`.

## Known issues

- **MinIO image.** MinIO removed its images from Docker Hub, and `quay.io/minio/minio` refuses anonymous pulls. The
  pinned tag `minio/minio:RELEASE.2025-09-07T16-13-09Z` must already be in local Docker; otherwise use
  `Playground:Blobs=local`. The README explains how to re-tag a local image.
- **Unmerged platform dependency.** The Files page needs Layouts.Default from `feat/mudtail-explorer`.
- **Module unload.** On a released platform, every runtime module (even the Greeting sample) reports
  `unloaded=false` right after an unload and is collected later. This is a platform issue in `ModuleRuntime`, not a
  Storage or AWS SDK leak. The fix is on Platform `fix/module-unload`, where Storage was checked to unload in the same
  request. It is not merged yet.
- **404 after sign-in.** After sign-in, the redirect to a module route such as `/files` shows 404 until the page is
  reloaded, because the client still has the anonymous module catalog. The fix is on Platform
  `fix/module-route-after-login`. It is not merged yet.
- **Phase 4 gaps.** Share, Security (the ACL dialog) and Edit (the image editor) are disabled in the Explorer. The API
  for access lists already exists.
- **No bundle yet.** The parts are installed by hand.
