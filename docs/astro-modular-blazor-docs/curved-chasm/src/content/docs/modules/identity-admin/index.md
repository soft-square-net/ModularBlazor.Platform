> **Status:** phases 1–3 are done on branch `feat/identity-admin` of the repository `ModularBlazor.Module.Admin.OpenIddict`
> (module `identity-admin` 1.0.0). It needs the identity service's **service admin API**, which is on the Platform branch
> `feat/identity-service-admin`. That branch is not in a platform release yet.

**Identity admin** manages a tenant's people and their access. **It owns no data.**

- Accounts, memberships, tenant profiles, sessions and OpenIddict clients stay in the **identity service**
  (`WebApi.Identity.Server`).
- Permissions and grants stay in the **WebApi host's grant store** (`IGrantStore`).

The module is the gateway between them. On each request it checks what the caller may do: the module and platform
permissions, the request's tenant, and the rules about acting on yourself. Then it calls the identity service as its
own confidential client.

Dependencies:

- The client module lists `WebApi.Modules.IdentityAdmin.Client` in `Dependencies`, so the API client is loaded first.
- The server module uses the platform contracts `IAccessScopes`, `ITenantContext`, `IGrantStore` and
  `IPermissionCatalog`, plus `RequirePermission(...)` on its routes.
- It calls the identity service at `IdentityAdmin:Authority`. When that is empty, it uses the host's `Auth:Authority`.
- It gets a **client-credentials** token for `webapi-identity-admin` with the scope `identity.admin` and caches it until
  shortly before it expires. That token's audience is `modular-identity`, so the WebApi never accepts it; only the
  identity service's service admin API does.
- Every call names the acting user in `X-Acting-User`.

The identity service side is documented in `src/WebApi/Identity/WebApi.Identity.Server/README.md` on
`feat/identity-service-admin`, sections "Service admin API", "Sessions" and "Platform admin API".

## Permissions and access model

The module declares two permissions. It also relies on two platform permissions.

| Permission | Owner | Lets the caller |
| --- | --- | --- |
| `identity.members.read` | identity-admin | See the tenant's members, their accounts, their access and their sessions |
| `identity.members.manage` | identity-admin | Invite, edit, suspend, re-activate and remove members; end sessions |
| `access.grants.manage` | platform | Grant and revoke standing permissions in the tenant |
| `platform.tenants.manage` | platform (platform admins) | Everything above in any tenant, plus the platform pages |

These are the exact permission sets the endpoints check (`IdentityAdminPermissions`):

| Set | Any of |
| --- | --- |
| Readers | `identity.members.read`, `identity.members.manage`, `access.grants.manage`, `platform.tenants.manage` |
| Managers | `identity.members.manage`, `platform.tenants.manage` |
| Granters | `access.grants.manage` (platform admins hold it in every tenant) |
| Platform admins | `platform.tenants.manage` |

Rules:

- **Tenant.** Every endpoint except the `/platform` ones works inside the request's tenant. A tenant admin's token names
  the tenant. A platform admin's token names none, so the pages show a tenant picker and send `X-Tenant`. Without a
  tenant, a call gives 400.
- **Not yourself.** A caller can not do these things to themself (409): suspend, remove, change their own role to
  anything but `tenant-admin`, or end all of their own sessions. On the platform pages a caller can not lock themself,
  sign themself out everywhere, or take their own platform-admin role. Their own current session can not be ended either
  (409, "sign out instead"). The current session is the one whose authorization id (`oi_au_id`) the access token carries.
- **Grantable permissions.** These are every module permission, plus `access.grants.manage`. All other platform
  permissions come from platform roles and are never granted in a tenant.
- **Grant scopes.** A scope is `tenant`, or a `kind:id` such as `press:{id}` or `category:{id}`. A suspended member
  gets no new grants (409).
- **Shift grants** (source `shift:{id}`) are written by the Shifts rota. They are shown read-only and revoking one
  gives 409. Grants from other writers (for example dev seeding) can not be revoked here either.
- **Removing a member** also revokes their standing grants in the tenant. Shift grants stay with their rota, but they
  can not be used without a membership.

Other modules check these grants. Contents checks a post's press and category scopes. Shifts writes `shift:{id}` grants
that are valid only during the shift. Elsa workflows check `workflow.*`.

The client module is open to every signed-in user. Pages show and hide actions according to
`GET /capabilities` (`canRead`, `canManage`, `canGrant`) and `GET /platform/capabilities`. The server checks again on
every call.

## API reference

The routes are under `/api/identity-admin`. Bodies are JSON (web casing). Most responses pass the identity service's
answer through: `Member`, `MemberInvited`, `MemberStatusChanged`, `MemberRemoved`, and the platform records. The record
definitions are in `Contracts.cs` and `PlatformContracts.cs`. The OpenAPI document is `src/openapi/identity-admin.json`.

### Members and access

| Method and route | Permission set | Request → response |
| --- | --- | --- |
| `GET /capabilities` | signed in | → `AdminCapabilities {userId, tenant, canRead, canManage, canGrant, problem}`. `problem` is a configuration problem, or null |
| `GET /members?search=` | Readers | → `Member[]`. The search matches the email or a name |
| `GET /members/{userId}` | Readers | → `Member` |
| `POST /members` | Managers | `{email, role?, displayName?, jobTitle?}` → 201 `MemberInvited {userId, status, newAccount}`. The role is `member` (default) or `tenant-admin`. An unknown address gets a new account without a password |
| `PUT /members/{userId}` | Managers | `{role?, displayName?, jobTitle?}` → `Member`. Null leaves a value unchanged; `""` clears a profile field |
| `POST /members/{userId}/suspend` | Managers | → `MemberStatusChanged {userId, tenant, status, revokedAuthorizations}`. The member's sessions in the tenant end at once |
| `POST /members/{userId}/activate` | Managers | → `MemberStatusChanged`. An invited member has to accept the invitation instead |
| `DELETE /members/{userId}` | Managers | → `MemberRemoved {userId, tenant, removed, revokedAuthorizations}`. It also revokes the member's standing grants |
| `GET /permissions` | Readers | → `PermissionGroup[] {moduleId, moduleName, permissions: [{name, description}]}`. Only grantable permissions are listed |
| `GET /members/{userId}/access` | Readers | → `MemberAccess {userId, permissionsNow[], grants: MemberGrant[]}`. Standing and shift grants are listed, ended ones included |
| `POST /members/{userId}/grants` | Granters | `{permission, scope = "tenant", validFrom?, validTo?}` → 201 `MemberGrant` |
| `DELETE /members/{userId}/grants/{grantId}` | Granters | → 204. Only standing grants can be revoked |

`MemberGrant` has these fields: `id`, `permission`, `scope`, `scopeKind` (`tenant`, `press`, `category`, …), `scopeId`,
`validFrom`, `validTo`, `source`, `sourceKind` (`standing`, `shift`, or another writer), `shiftId`, `activeNow`,
`ended`, `editable`, `createdAt` and `createdBy`.

### Sessions

A **session** is one sign-in of a member in this tenant. It is a tenant-bound authorization in the identity service,
plus the tokens issued under it.

| Method and route | Permission set | Request → response |
| --- | --- | --- |
| `GET /sessions?userId=&includeEnded=` | Readers | → `MemberSession[]` (`id, userId, email, displayName, clientId, application, scopes, createdAt, lastUsedAt, expiresAt, status, active, validTokens, current`) |
| `POST /sessions/{sessionId}/revoke` | Managers | → `SessionsRevoked {tenant, userId, revokedSessions}`. Your own current session gives 409 |
| `POST /members/{userId}/sessions/revoke` | Managers | → `SessionsRevoked`. Ends every sign-in of the member in this tenant. Not allowed on yourself |

Ending a session revokes its tokens. That browser must also sign in again before the identity service issues anything
more for this tenant; without that, the browser would get a new token silently through its identity cookie. Access
tokens that were already issued stay valid until they expire, at most 10 minutes. Other tenants are not affected.

### Platform (`platform.tenants.manage`, no tenant needed)

| Method and route | Request → response |
| --- | --- |
| `GET /platform/capabilities` (any signed-in user) | → `PlatformCapabilities {userId, isPlatformAdmin, problem}` |
| `GET /platform/tenants` | → `TenantPolicy[] {tenantId, displayName, requireMfa, active, invited, suspended}` |
| `PUT /platform/tenants/{tenant}` | `{displayName?, requireMfa?}` → `TenantPolicy`. The new policy applies from the next token |
| `GET /platform/accounts?search=`, `GET /platform/accounts/{userId}` | → `Account` (lockout, two-factor, password set, `platformRoles`, `memberships`) |
| `POST /platform/accounts/{userId}/lock`, `/unlock`, `/sign-out` | → `AccountChanged {userId, action, revokedSessions}`. Locking ends every session everywhere |
| `PUT /platform/accounts/{userId}/roles` | `{platformAdmin}` → `AccountChanged` |
| `GET /platform/applications`, `GET /platform/applications/{clientId}` | → `ClientApplication` (`managedBy` is `config` for a built-in client or `ui` for one managed here, plus `rotation`, `liveTokens`, …) |
| `POST /platform/applications` | `ClientApplicationRequest` → 201 `ClientApplicationCreated {application, secret?}` |
| `PUT /platform/applications/{clientId}`, `DELETE /platform/applications/{clientId}` | Changes or deletes a client managed here. A built-in client gives 409 |
| `POST /platform/applications/{clientId}/secret` | → `ClientSecret {clientId, secret, mode}`. The mode is `created`, `replaced` or `rotation-started`. The secret is shown once; the identity service keeps only its hash |
| `POST /platform/applications/{clientId}/rotation/complete`, `/rotation/cancel` | Ends a secret rotation (see below) |
| `POST /platform/applications/{clientId}/tokens/revoke` | → `ClientTokensRevoked {clientId, revokedAuthorizations, revokedTokens}` |
| `GET /platform/scopes` | → `ScopeInfo[] {name, displayName, description, resources, builtIn}` |

**Built-in clients** (`blazor-client`, `elsa-workflows`, `webapi-identity-admin`, `scalar-client`) come from the
identity service's configuration and are read-only here. Their secret is rotated with an **overlap window**:

1. **Rotate secret** starts the rotation and shows the new secret once. The old and the new secret both work.
2. Put the new secret where the client reads it, then restart that client. The repository README lists the
   configuration keys for `elsa-workflows` and `webapi-identity-admin`.
3. **Complete rotation** is enabled once a token was issued with the new secret. Completing it makes the old secret
   stop working. **Cancel rotation** drops the new secret instead.

**Extra clients** are created on the Clients page. They can use code flow with PKCE, refresh tokens and client
credentials. The page never offers `identity.admin`, and the identity service's seeder never touches these clients.

### Errors

Every error is a problem-details response (`application/problem+json`).

| Status | When |
| --- | --- |
| 400 | No tenant on a tenant route; a permission that can not be granted; a bad grant scope; a validation problem from the identity service (its `errors` are kept) |
| 401 | Not signed in |
| 403 | The caller lacks the route's permission set (`RequirePermission`) |
| 404 | Not a member, or no such account, client, session or grant |
| 409 | An action on yourself; a suspended member; a shift grant or another writer's grant; a built-in client changed or deleted; the identity service's own conflicts (for example "already a member") |
| 502 | The identity service refused the module's own token (it answered 401 or 403 to `webapi-identity-admin`), or it sent no token |
| 503 | The module is not configured (no authority URL, no client secret), or the identity service can not be reached |

For other errors, the identity service's status and message are passed through. Its `error` code becomes the problem's
`title`.

## Settings and secrets

The defaults are in the module manifest. Change them on the host's **Host Modules** page, or as host overrides:
`Modules:Settings:identity-admin:{key}`, which is `Modules__Settings__identity-admin__…` as environment variables.

| Key | Default | Notes |
| --- | --- | --- |
| `IdentityAdmin:Authority` | empty | Empty: the host's `Auth:Authority` |
| `IdentityAdmin:ClientId` | `webapi-identity-admin` | |
| `IdentityAdmin:ClientSecret` | empty | **Secret.** Set it as a host override from a secret store, never in the module catalog. While it is missing, `problem` explains this and every identity call gives 503 |
| `IdentityAdmin:Timeout` | `00:00:15` | HTTP timeout for calls to the identity service |

The identity service must have the same secret configured for `webapi-identity-admin` (`Identity:AdminClient`). It does
not register that client while the secret is missing. The development values are in the identity service's
`appsettings.Development.json` and in the playground's `AppHost.cs`. Read them there; do not copy them into documents.

## UI pages

All pages are under `/identity`. A platform admin also gets a tenant picker, and a **Platform** tab that opens the
platform pages.

| Route | Page | What it does |
| --- | --- | --- |
| `/identity` | Members | Lists the tenant's members (invited, active, suspended), with search. Invite, suspend, re-activate and remove. A row opens the member |
| `/identity/members/{userId}` | Member | Profile and role in the tenant, the account's state, and access: standing grants (add, revoke) and shift grants (read-only). Also the member's sessions, which can be ended one at a time or all at once |
| `/identity/sessions` | Sessions | Every member's active sign-ins in the tenant, and on request the ended and revoked ones. End one; your own is marked |
| `/identity/platform/tenants` | Tenants | Each tenant's name on the sign-in pages, whether it requires MFA, and its members by status. Tenants from the platform's directory that the identity service has not seen yet are listed too; setting their policy creates them |
| `/identity/platform/accounts` | Accounts | Global accounts. Lock, unlock, sign out everywhere, and grant or take the platform-admin role |
| `/identity/platform/clients` | Clients | The identity service's clients: built-in ones and ones managed here |
| `/identity/platform/clients/{clientId}` | Client | Edit a client managed here, or view a built-in one. New secret, secret rotation, revoke tokens, delete. `new` creates a client |
| `/identity/platform/scopes` | Scopes | Read-only: the scopes a client may ask for, and the APIs they give access to |

## Install and activation

1. **Platform.** The identity service must have the service admin API: Platform branch `feat/identity-service-admin`,
   until it is released.
2. **Server part.** Zip the build output of `WebApi.Modules.IdentityAdmin` (`bin/<Configuration>/net10.0`). Upload it on
   the **Host Modules** page, activate it, and set `IdentityAdmin:ClientSecret` as a host override.
3. **Client parts.** Upload them on the **Client Modules** page, the API client first:
   1. `soft.square.net.WebApi.Modules.IdentityAdmin.Client.dll`
   2. `soft.square.net.Module.IdentityAdmin.dll`
4. **Grant access.** Grant `identity.members.read` or `identity.members.manage`, and `access.grants.manage` where it is
   needed, to the tenant's admins.

To build and test: `dotnet build` and `dotnet test`. Restoring needs `GITHUB_PACKAGES_TOKEN`, a token with
`read:packages` for the soft-square-net feed. `global.json` pins the module SDK. After an endpoint change, export the
OpenAPI document again with `src/WebApi/scripts/Export-ModuleOpenApi.ps1` from a Platform checkout, with
`-ModuleId identity-admin`. The next build regenerates the client. Commit both.

## Developing with the playground

```bash
dotnet run --project playground --launch-profile dev -p:PlatformRoot=<a Platform checkout on feat/identity-service-admin>/
```

The playground runs PostgreSQL (with pgAdmin), the identity service on port 5090, one WebApi on 5080 and the Blazor
client on 5070. These are the platform lab's ports, so stop the lab and other playgrounds first.

| Profile | What it does |
| --- | --- |
| `dev` | The WebApi loads the module and its client parts from their build output. Rebuild, then restart the `webapi` resource |
| `install` | Starts without the module, as in production. Each build writes `playground/out/identity-admin.zip` and the client DLLs, to upload by hand |

The playground sets the module's client secret for Development. It also gives dev accounts in tenant `acme` grants
through `Access:DevGrants`:

| Account | Gets |
| --- | --- |
| `acme-admin@modular.local` | `identity.*` and `access.grants.manage` in `acme` |
| `editor@modular.local` | `identity.members.read` in `acme` |
| `admin@modular.local` | Platform admin: every tenant through the picker, and the platform pages |

The passwords are in the identity service's `appsettings.Development.json`. Data stays in the Docker volume
`identity-admin-playground-data` and in `playground/.data`. Delete both to start over.

## Known issues

- **Unreleased platform dependency.** The service admin API, the `identity.admin` scope and the `webapi-identity-admin`
  client exist only on Platform `feat/identity-service-admin`. With an identity service built from another branch, the
  module can not get its token, and its calls fail.
- **Revoking takes effect slowly.** Ending a session or suspending a member stops token renewal at once, but access
  tokens already issued stay valid for up to 10 minutes.
- **Old module leftovers.** `playground/.data` may still contain the client parts of the old `AdminOpeniddict` module
  from earlier runs. Remove them on the Client Modules page.
- **No bundle yet.** The server and client parts are installed by hand; there is no `.modpkg` bundle for this module.
